# sandvik as a library: the embedding API

This directory turns sandvik into something a **host process** can drive:

* `sandvik_c.h` — the plain C API (opaque `sv_vm*` handle, no C++ and no JNI types).
* `sandvik_c.cpp` — the implementation, the only translation unit that mixes the C API with the C++ VM.
* `sandvik_jni.cpp` — JNI entry points (`Java_org_sandvik_Native_*`) for a host **JVM**.

It is milestone **M1** of the integration plan described in `../UNIDBG_EVAL.md`
(§11.3): the host JVM owns the process, sandvik is a normal JNI library inside
it, and no ARM emulator is involved yet.

## Build

The three files are part of the `sandvik` shared library (`libsandvik.so` /
`libsandvik.dll`), nothing else has to be enabled:

```sh
cmake -S . -B build -G Ninja -DSANDVIK_TESTS=ON
cmake --build build -j 8
```

Two build details matter:

* `CMakeLists.txt` adds the **real** `<jni.h>` (from the JDK found by CMake) only to
  this library target. sandvik's own JNI dialect stays in `src/jni/jni.h`, which is
  only ever included as `"jni/jni.h"`; the two must not meet in one TU.
* On Windows the library is linked with `-Wl,--export-all-symbols`, so both the
  test executables and a host JVM can resolve `Java_org_sandvik_Native_*`.

## C usage

```c
#include "api/sandvik_c.h"

sv_vm* vm = sv_vm_create();
sv_set_log_level(0);                                     /* before create() to silence the banner */
sv_vm_load_rt_file(vm, "android/12.0.0/bin/core-oj.dex.jar");
sv_vm_load_rt_file(vm, "android/12.0.0/bin/core-libart.dex.jar");
sv_vm_load_rt_file(vm, "android/12.0.0/bin/icu-stubs.dex.jar");
sv_vm_load_dex(vm, "classes.dex");

const char* args[] = { "s:world" };
sv_value value;
if (sv_vm_call_static(vm, "BridgeHello", "hello", "(Ljava/lang/String;)Ljava/lang/String;", args, 1, &value) == 0) {
    printf("%s\n", value.string_value);                  /* hello, world */
    sv_value_dispose(&value);
} else {
    fprintf(stderr, "%s\n", sv_vm_last_error(vm));
}
sv_vm_destroy(vm);
```

## Host JVM usage

```java
Native.setGlobalLogLevel(0);
long vm = Native.create();
Native.loadRtFile(vm, ".../core-oj.dex.jar");
Native.loadRtFile(vm, ".../core-libart.dex.jar");
Native.loadRtFile(vm, ".../icu-stubs.dex.jar");
Native.loadDex(vm, "tests/java/bridge/classes.dex");
Object[] value = Native.callStatic(vm, "BridgeHello", "hello",
                                  "(Ljava/lang/String;)Ljava/lang/String;", new String[] { "s:world" });
// value = { Integer kind, String text, Long number, String className }
Native.destroy(vm);
```

The library is located with `-Dsandvik.library=<path to libsandvik.dll>`; without
the property the normal library search path is used.

### Argument tokens

| token        | Java type          |
| ------------ | ------------------ |
| `s:<text>`   | `java.lang.String` |
| `i:<int>`    | `int`              |
| `l:<long>`   | `long`             |
| `d:<x>`      | `double`           |
| `n:`         | `null`             |

A token without a known prefix is treated as a string.

### Value kinds

`SV_KIND_NULL` (0), `SV_KIND_STRING` (1, `string_value`), `SV_KIND_INT` (2) and
`SV_KIND_BOOL` (5, `int_value`), `SV_KIND_LONG` (3, `long_value`),
`SV_KIND_DOUBLE` (4, `double_value`), `SV_KIND_OBJECT` (6, `class_name` holds the
class descriptor of the object).

## Acceptance test

```sh
ctest --test-dir build -R bridge_jvm --output-on-failure
# or by hand
java --enable-native-access=ALL-UNNAMED -Dsandvik.library=<abs path>/libsandvik.dll \
     -cp build/bridge-classes org.sandvik.BridgeTest <repo root>
```

The test loads a dex file and asks the VM for two values: a `String` from
`BridgeHello.hello(String)` and an `int` from `BridgeHello.add(int, int)`. It is
registered by CMake as the `bridge_jvm` test; the host classes and the dex under
test are (re)generated by the `bridge_classes` target.

## Limits of this first slice

* only **static** methods are callable;
* arguments are limited to the tokens above — arbitrary Java objects cannot cross
  the boundary yet (the plan's M2/M3 milestones in `../UNIDBG_EVAL.md` §11.3);
* each call runs on a fresh sandvik thread, and the handle is **not**
  thread-safe: call one method at a time;
* a failure surfaces as a negative return plus `sv_vm_last_error()`; the Java
  exception object of the interpreted code is not marshalled yet (only its text,
  when the C++ layer reports it);
* this API is host → sandvik. It does not change sandvik's own JNI support for the
  *interpreted* code (see `src/jni.cpp`).
